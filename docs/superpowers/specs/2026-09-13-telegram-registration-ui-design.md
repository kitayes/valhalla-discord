# Регистрация в Telegram: одна строка, inline-кнопки, карточка подтверждения

Дата: 2026-09-13
Статус: дизайн, к реализации не приступали

## Задача

Регистрация команды сегодня — 7 игроков × 6 вопросов подряд («Введите Game
ID:», «Введите Zone ID:», …) с reply-клавиатурой снизу. Капитан отвечает на
~40 сообщений, не видит, что уже ввёл, и в конце получает «Регистрация
завершена!» без возможности проверить состав. Ошибка в третьем игроке
обнаруживается судьями в день турнира.

Что меняем:

1. **Игрок одной строкой.** `Ник GameID ZoneID Звёзды [@контакт]` вместо пяти
   вопросов. Роль — кнопками, чтобы не было опечаток.
2. **Inline-кнопки** для всего, что внутри потока: роли, «Пропустить»,
   «Отмена», «Подтвердить», «Исправить N». Reply-клавиатура остаётся только
   для главного меню (это команды).
3. **Итоговая карточка.** В конце — весь состав и кнопки «✅ Подтвердить» /
   «✏️ N» / «🗑 Удалить». Ничего не «завершается» молча.

Соло-регистрация проходит тот же путь: строка → роль → карточка.

Схема БД не меняется.

## Поток команды

```
/reg_team
  «Название команды:»                                  [❌ Отмена]
Название
  «Команда 'X' создана.
   👑 Игрок 1/7 (капитан)
   Отправь одной строкой: Ник GameID ZoneID Звёзды
   Пример: Kitayes 123456789 1234 25»                  [❌ Отмена]
Строка
  «Kitayes · 123456789 (1234) · 25⭐
   Роль?»                    [Gold][Exp][Mid] [Roam][Jungle] [❌ Отмена]
Роль (тап)
  «✅ Игрок 1: Kitayes — Mid
   👤 Игрок 2/7
   Отправь: Ник GameID ZoneID Звёзды [@telegram]»      [❌ Отмена]
… слоты 2–5 так же
  слот 6, 7: «🔁 Замена 6/7 …»            [⏭ Пропустить] [❌ Отмена]
После 7-го (или пропуска)
  «Команда 'X'
   1. 👑 Kitayes · Mid · 123456789 (1234) · 25⭐
   2. 👤 Vasya · Gold · … · @vasya
   …
   6. 🔁 …
   Всё верно?»
                                            [✅ Подтвердить]
                                            [✏️ 1][✏️ 2][✏️ 3][✏️ 4][✏️ 5][✏️ 6][✏️ 7]
                                            [🗑 Удалить команду]
✏️ N  → снова строка для игрока N → роль → карточка снова
✅    → «Команда зарегистрирована. В день турнира нажми /checkin.» + главное меню
🗑    → команда удаляется (как /delete_team), главное меню
```

Кнопки «✏️ N» показываются только для слотов, где есть игрок.

Уже подтверждённую команду можно править: `/my_team` показывает ту же
карточку с кнопками «✏️ N», «🗑 Удалить» и «➕ Замена» (если замен меньше
двух), но без «✅ Подтвердить» — каждая правка записывается сразу, после неё
карточка показывается снова. Старый `/edit_player N` остаётся синонимом
«✏️ N».

## Поток соло

```
/reg_solo
  «Отправь одной строкой: Ник GameID ZoneID Звёзды»    [❌ Отмена]
Строка → «Роль?» [кнопки] → карточка
  «Kitayes · Mid · 123456789 (1234) · 25⭐
   Всё верно?»                              [✅ Подтвердить] [✏️ Исправить]
```

## Парсер строки

`parsePlayerLine(s string) (playerLine, error)` — чистая функция в
`internal/application`.

- Разделители: пробелы и/или запятые, любое количество.
- Токены с `@` в начале — контакт (не более одного). Извлекаются первыми.
- Из оставшихся: ник — все токены до первого числового; потом ровно три
  числовых токена: GameID, ZoneID, звёзды. ZoneID принимается и как `(1234)`.
- Числовой токен — только цифры (после снятия скобок). GameID и ZoneID
  хранятся строками, как сейчас; звёзды — `int ≥ 0`.
- Ник: 1–64 символа. Лишние токены после звёзд — ошибка.

Ошибки — конкретные, с указанием, чего не хватило:

| Ввод | Ответ |
|---|---|
| `Kitayes 123456789` | «Не вижу Zone ID и звёзды. Формат: Ник GameID ZoneID Звёзды» |
| `123456789 1234 25` | «Не вижу ник — он должен идти первым» |
| `Kitayes 123456789 1234 много` | «Звёзды — число. Формат: …» |
| `Kitayes 123456789 1234 25 лишнее` | «Не понял 'лишнее'. Формат: …» |

При ошибке состояние не двигается, пользователь просто отправляет строку
снова.

Контакт у капитана (слот 1) игнорируется — его Telegram и так известен и
обновляется каждым сообщением.

## Состояния FSM

Хранятся в `telegram_players.fsm_state`, как сейчас. Старые
`team_reg_{nick,id,zone,rank,role,contact}_N` и
`waiting_{nickname,game_id,zone_id,stars,role}` уходят.

| Состояние | Ждём | Дальше |
|---|---|---|
| `waiting_team_name` | текст | `team_line_1` |
| `team_line_N` | строка игрока N | `team_role_N` |
| `team_role_N` | `reg:role:*` | `team_line_N+1`, либо `team_confirm` после 7 / пропуска |
| `team_fix_N` | строка игрока N (правка до подтверждения) | `team_fixrole_N` |
| `team_fixrole_N` | `reg:role:*` | `team_confirm` |
| `team_edit_N` | строка игрока N (правка/добавление после подтверждения, из `/my_team`) | `team_editrole_N` |
| `team_editrole_N` | `reg:role:*` | Idle + карточка `/my_team` |
| `team_confirm` | `reg:confirm` / `reg:fix:N` / `reg:delete` | Idle / `team_fix_N` / Idle |
| Idle (`/my_team`) | `reg:fix:N` / `reg:sub` / `reg:delete` | `team_edit_N` / `team_edit_{len+1}` / Idle |

`team_fix_N` и `team_edit_N` работают одинаково по данным: если строка с
позицией N есть в `GetTeamMembers` — обновляем её по `id`; если N на единицу
больше числа игроков — вставляем новую замену. Различаются только тем, куда
возвращаются после роли.
| `solo_line` | строка | `solo_role` |
| `solo_role` | `reg:role:*` | `solo_confirm` |
| `solo_confirm` | `reg:confirm` / `reg:fix` | Idle / `solo_line` |

`reg:skip` принимается только в `team_line_6` / `team_line_7`.
`reg:cancel` — в любом состоянии регистрации → Idle (как «Отмена» сейчас).

Текст в состоянии, где ждём кнопку (`*_role_*`, `*_confirm`), отвечает
подсказкой «Нажми кнопку выше» и не двигает состояние. Роль текстом тоже
принимается, если совпадает с белым списком — на случай клиентов без inline.

Данные о текущем игроке между `line` и `role` живут в БД: для капитана —
в его строке, для тиммейта — во вставленной строке (см. ниже). Ничего не
держим в памяти процесса.

## Callback data

Формат как у ставок: `reg:<action>[:<arg>]`, разделитель `:`.

| Data | Где принимается |
|---|---|
| `reg:role:<Gold\|Exp\|Mid\|Roam\|Jungle>` | `*_role_*`, `*_fixrole_*` |
| `reg:skip` | `team_line_6`, `team_line_7` |
| `reg:cancel` | любое состояние регистрации |
| `reg:confirm` | `team_confirm`, `solo_confirm` |
| `reg:fix:<1..7>` | `team_confirm` → `team_fix_N`; Idle с командой (карточка `/my_team`) → `team_edit_N` |
| `reg:fix` | `solo_confirm` |
| `reg:delete` | `team_confirm`, Idle с командой |
| `reg:sub` | Idle с командой, если замен меньше двух |

Роль и номер слота валидируются по белому списку — callback data приходит от
клиента и не является фактом. Callback вне ожидаемого состояния → alert «Эта
кнопка больше не действует», состояние не трогаем.

После обработки любого `reg:*` у сообщения с кнопками убираем клавиатуру
(`EditMessageReplyMarkup` на пустую), чтобы повторный тап ничего не делал.
Ответ — новым сообщением.

Диспетчер в `Bot.handleCallbackQuery`: префикс `reg:` → регистрация; иначе →
`bettingBot.HandleCallback` как сейчас. Если `bettingBot == nil`, `reg:`
всё равно работает.

## Данные

- Слот 1 (капитан): строка → `UpdatePlayerField` по `telegram_id` для
  `game_nickname`, `game_id`, `zone_id`, `stars`; роль → `main_role`.
- Слоты 2–7: строка → **одна** вставка `CreateTeammate` со всеми полями
  (`team_id, game_nickname, game_id, zone_id, stars, telegram_username,
  is_substitute`). `CreateTeammate` расширяется, `UpdateLastTeammateData`
  остаётся только чтобы записать роль в только что вставленную строку.
- `team_fix_N`: целевая строка — `GetTeamMembers(teamID)[N-1]` (отсортировано
  по `id`, слот 1 — капитан, т.к. его строка старше). Правим через
  `UpdatePlayerFieldByID`. Для капитана `telegram_username` не трогаем.
- Карточка собирается из `GetTeamByID` + `GetTeamMembers`. Слот `N` игрока —
  его индекс + 1 в этом списке.
- Пропуск: «⏭» на слоте 6 переходит к слоту 7, «⏭» на слоте 7 — к карточке.
  Команда с одной заменой — нормальный случай. Номер слота в карточке — это
  позиция в `GetTeamMembers`, поэтому после пропуска 6 единственная замена
  показывается как «6», а не «7»; кнопка «➕ Замена» появляется, пока
  замен меньше двух.

## Где живёт код

- `internal/application/telegram_registration.go` — новый файл: парсер,
  FSM регистрации (`handleRegistrationInput`, `HandleRegAction`), сборка
  текста карточки. `telegram_service.go` худеет: из `HandleUserInput`
  уходят ветки регистрации, остаётся диспетчер по префиксу состояния.
- Интерфейс `TelegramService` получает
  `HandleRegAction(ctx, tgID int64, action, arg string) (string, string)`.
- Возвращаемый `kbType` расширяется: `"reg_roles"`, `"reg_skip"`,
  `"reg_cancel"`, `"reg_confirm:<slots>"` (какие ✏️ рисовать, через запятую),
  `"reg_solo_confirm"`. Delivery по нему строит inline-клавиатуру;
  старые `role`/`skip`/`cancel` (reply) удаляются.
- `internal/delivery/telegram/registration.go` — новый файл:
  `handleRegCallback`, конструкторы inline-клавиатур, снятие клавиатуры с
  отработавшего сообщения.
- `internal/repository/telegram_postgres.go` — `CreateTeammate` со всеми
  полями.

## Тесты

- Парсер: табличный тест, все строки из раздела «Парсер» + граничные
  (скобки, запятые, `@контакт` в середине, ник из двух слов).
- FSM: на `fakeTelegramRepo` — полный happy-path команды (7 слотов),
  пропуск 6 и 7, правка через `reg:fix:3` и возврат на карточку,
  callback вне состояния, текст в состоянии-кнопке, соло полный путь,
  отмена из середины.
- Delivery: диспетчер `reg:` vs `bet:`, парсинг `reg:*` с мусором в аргументе.
- Репозиторий: `CreateTeammate` со всеми полями — в интеграционный набор.

## Что не делаем

Главное меню — как есть. Админ-команды — как есть. Редактирование названия
команды, перенос игроков между командами, языки, миграции — нет. Старые
состояния `team_reg_*` у людей, зависших посреди регистрации на момент
деплоя, просто сбрасываются в Idle с «Начните заново: /reg_team».
