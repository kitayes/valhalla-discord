# Сопоставление таблицы результатов с составом лобби

Дата: 2026-09-09
Статус: дизайн, к реализации не приступали

## Задача

Матч живёт в двух несвязанных мирах.

**Лобби** знает состав точно: `lobby_matches.team_a_ids` и `team_b_ids` — десять
`player_id`, и каждый из них с недавних пор привязан к Discord-аккаунту через
`/bind`. По этому составу считается Elo.

**Скриншот** даёт десять строк с никами, которые распознала модель. Их
раскладывает `MatchPostgres.Create`, вызывая `EnsurePlayerExists(p.PlayerName)`
на каждое имя. Эта функция ищет по всей таблице `players`: сначала точное
совпадение, потом — нечёткое, через косинусную близость эмбеддингов.

Связи между мирами нет: в `matches` нет ссылки на `lobby_matches`, а
`expectedPlayers` доезжает только до промпта Gemini и на разбор результата не
влияет.

### Что из-за этого ломается

1. **Фантомные игроки.** Модель исказила ник — `EnsurePlayerExists` не нашла
   точного совпадения, эмбеддинги не дотянули до порога, создаётся новая строка
   в `players`. Реальному игроку матч не засчитан, `/players` засоряется.
2. **Чужая статистика.** Нечёткий поиск дотянул до порога, но попал в *похожего
   другого* игрока. Результаты уезжают ему.
3. **Расходящийся профиль.** Elo и MMR считаются по составу лобби, а KDA
   пишется на те строки `players`, которые вернул нечёткий поиск. Две половины
   профиля одного человека начинают жить отдельно.

Причина у всех трёх одна: **ключом служит ник, а ник — изменяемая строка.**
Человек меняет ник, играет со смурфа, берёт чужой аккаунт — и связь рвётся.

### Что мы знаем взамен

Личность участника матча — это **состав лобби**, а не подпись на скриншоте. Ник
надо понизить до подсказки.

## Решение

Сопоставлять десять строк скриншота с десятью известными `player_id` лобби,
используя ник как хинт, а не как ключ. Неопознанное добивать вычитанием
**внутри команды**, а не по всему составу. Что не добилось — отдавать судье.

### Опора: скриншот делится на две пятёрки

Каждая строка несёт `PlayerResult.Result` — `WIN` или `LOSE`. Значит скриншот
сам разваливается на две пятёрки. Какая пятёрка какой команде лобби
соответствует, на момент загрузки неизвестно: скриншот обрабатывается **до**
нажатия кнопки WIN (медали сохраняются на лобби-матч заранее, судья закрывает
матч потом). Сторона определяется по перекрытию ников — если большинство
опознанных ников WIN-стороны сидят в команде A, значит WIN-сторона это A.

### Алгоритм

```
1. Развести строки скриншота на WIN-пятёрку и LOSE-пятёрку по Result
2. Сопоставить стороны с командами лобби по числу совпавших ников
   ├─ перекрытие однозначное  → дальше
   └─ ничья или мусор         → шаг 5 (судья)
3. Внутри каждой стороны сопоставить по нику: точное совпадение, затем алиасы
4. Внутри стороны остался ровно один неопознанный игрок лобби
   и ровно одна неопознанная строка → это друг друга, связать
5. Всё прочее → селект судье: «строка «Bjorn» — кто это?» со списком
   неопознанных участников этой команды
```

Шаг 4 — ядро. Он превращает «один из десяти» в «один из пяти» и тем самым
решает случай, который без разбиения по командам неразрешим:

> Гуннар (команда B) играет с аккаунта Бьорна; Бьорн в лобби в команде A и
> играет с какого-то третьего аккаунта.
>
> ```
> сторона A: ждём Бьорна  → неопознанная строка «SomeNick» → это Бьорн
> сторона B: ждём Гуннара → неопознанная строка «Bjorn»    → это Гуннар
> ```
>
> Глобально это «двое неопознанных» и уход к судье. По корзинам — по одному в
> каждой, обе связываются однозначно.

### Что алгоритм не решает

| случай | исход |
|---|---|
| по одному неопознанному в каждой команде (1+1) | вычитание, автоматически |
| двое и больше неопознанных в **одной** команде (2+0) | судья |
| стороны скриншота не развелись по командам | судья |
| скриншот вне треда матча (состава лобби нет) | как сейчас: глобальный поиск |

Автоматически до конца это не решается в принципе: когда в одной корзине два
неизвестных, в данных нет информации о том, кто за каким аккаунтом сидел. Любая
схема, которая делает вид, что решает, будет уверенно врать. Поэтому шаг 5 —
не заглушка, а часть дизайна.

## Алиасы

Опознали строку вычитанием — значит узнали, что этот человек играл под этим
ником. Запоминаем, чтобы в следующий раз он совпал напрямую и вычитание не
тратилось.

**Учить алиас можно только если ник не принадлежит никому другому** — ни как
`players.name`, ни как чужой алиас.

Без этого правила случай с чужим аккаунтом отравляет базу: «Bjorn» опознан как
Гуннар верно *для этого матча*, но записать «Bjorn — алиас Гуннара» нельзя,
потому что Бьорн существует. Иначе со следующего матча статистика настоящего
Бьорна начнёт утекать Гуннару, и дальше по нарастающей.

Алиас, выбранный судьёй на шаге 5, учится по тому же правилу: подтверждение
человеком снимает неоднозначность, но не даёт права забрать чужой ник.

## Изменения в схеме

**`matches.lobby_match_id`** — ссылка на лобби-матч, из которого приехал
скриншот. Сейчас её нет вовсе, и связать записанный матч с составом задним
числом нечем. Nullable: матчи из скриншотов вне треда останутся без неё.

**`player_aliases`** — известные ники игрока.

```sql
CREATE TABLE player_aliases (
    id         SERIAL PRIMARY KEY,
    player_id  INT NOT NULL REFERENCES players(id) ON DELETE CASCADE,
    alias      VARCHAR(255) NOT NULL,
    source     VARCHAR(16) NOT NULL,   -- 'elimination' | 'referee'
    created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE UNIQUE INDEX idx_player_aliases_alias ON player_aliases(LOWER(TRIM(alias)));
```

Уникальность по нормализованному алиасу — это и есть машинная защита правила
«ник не может принадлежать двоим». Попытка выучить занятый ник упрётся в
нарушение уникальности, а не в проверку, которую можно забыть.

`player_nickname_history` не трогаем: это журнал админских `/rename_player`,
у него другая роль, и переиспользовать его под алиасы значило бы смешать аудит
с рабочим индексом.

## Слои

- **repository** — чтение состава лобби, чтение и запись алиасов, запись
  `matches.lobby_match_id`. Разрешение имён туда не уезжает: это правила, а не
  хранение.
- **application** — сам алгоритм сопоставления. Чистая функция над «состав
  лобби + строки скриншота + известные алиасы» → «связки + список
  неоднозначностей». Без БД и без Discord, поэтому проверяется таблично.
- **delivery/discord** — селект судье и применение его ответа. Компонентная
  обвязка уже есть, паттерн тот же, что в визарде создания матча.

Ядро — чистая функция. Всё, что делает решение спорным, происходит в ней, и
именно она должна быть покрыта тестами плотнее всего.

## Обработка ошибок

- Стороны не развелись → не пишем матч молча, идём к судье.
- Судья не ответил → матч остаётся незаписанным, скриншот можно перезалить.
  Ничего наполовину записанного не остаётся.
- Учёба алиаса упала на уникальности → это не ошибка обработки матча: связка
  для текущего матча уже верна, алиас просто не учится. Пишем Warn и идём
  дальше.
- Запись матча и связок — одной транзакцией. Полусвязанный матч хуже, чем
  незаписанный.

## Тестирование

**Юнит, на чистой функции сопоставления** — основной объём:
- все десять совпали по нику;
- один неопознанный в каждой команде → вычитание связывает верно;
- двое в одной команде → отдаётся судье, ничего не угадано;
- ник совпал с участником *другой* команды → не притягивается через границу;
- стороны с одинаковым перекрытием → отдаётся судье;
- алиас перекрывает точное совпадение по `players.name`? — нет, точное имя
  выигрывает.

**Интеграционные, по живой базе** (механика уже есть, `-tags integration`):
- учёба алиаса на свободном нике проходит;
- учёба на чужом нике отбивается уникальным индексом;
- матч со ссылкой на лобби пишется и читается.

## Вне рамок

- Разбор скриншота вне треда матча — остаётся как есть.
- Нечёткий поиск в `EnsurePlayerExists` не трогаем: для OCR он уместен, а в
  роли ключа его заменяет состав лобби.
- Слияние уже наплодившихся фантомных профилей — отдельная задача.
